# 仕様体系と全体構造

## 一意な正本

| 境界 | owner文書 | 主な定義 |
| --- | --- | --- |
| 製品・収集・配布 | `PRODUCT` / `docs/PRODUCT_REQUIREMENTS.md` | component境界、状態、起動、更新、Release、Workflow |
| REST wire | `WIRE` / `docs/REST_API_V1.md` | route、version別schema、header、容量、read-only effect |
| データ | `DATA` / `docs/DATA_PROTECTION_POLICY.md` | partition、transaction、backup、migration、保持、復旧 |
| 画面 | `UX` / `docs/WINDOWS_UX_SPEC.md` | Linux/Windows共通の表示意味、状態、Graph、操作 |
| 文言・時刻 | `I18N` / `docs/LOCALIZATION.md` | locale、固定文言、timezone、font |
| security | `SECURITY` / `SECURITY.md` | trust boundary、秘密、入力検証、残余risk |

README、DESIGN、runbook、このWiki、要求台帳は派生文書です。矛盾した場合はowner文書が優先され、派生文書を修正します。通常worktreeに`REQUIREMENTS.md`、`ACCEPTANCE.md`、`FINAL_ACCEPTANCE.md`、`VERIFICATION_PLAN.md`が存在しても、これらは`.gitignore`対象のlocal historical evidenceで、repository、Release、Wikiの構成物ではなく、現在の仕様・完了・PASSを決めません。このWiki整備で内容を変更・削除・追跡しません。

## 依存方向

```text
Codex app-server + validated Session JSONL
              ↓
Linux resident service（唯一のcollector / DB writer / publisher）
       ├─ profile・account単位のSQLite
       └─ immutable REST details generation
                 ├─ Linux X UI
                 └─ SSH local forwarding → Windows UI
```

UIはSQLite、Session、app-serverを直接読みません。現行表示rootは`GET /v3/details`一応答です。旧serviceがexact 404を返した場合だけv2、さらにexact 404の場合だけv1へ一段ずつfallbackし、応答や世代をmergeしません。clientとdaemonのproduct versionが異なっても、schema-validなAPI互換性があれば表示を継続します。

## 定義から証拠まで

各仕様項目は次の一方向で追跡します。

```text
owner文書のmaster ID → 派生台帳 → 実装入口 → 直接oracle → Release時の実環境証拠
```

実装やtestを正本へ逆輸入しません。未確認、未統合、失敗はそのまま記載し、実装済みやPASSへ読み替えません。詳細は[検証ハーネス](検証ハーネス)を参照してください。

要求の追加・変更、障害、Release準備では、[開発プロダクトライン](検証ハーネス#開発プロダクトライン)を1回ずつ起動します。影響を受けるownerを見直し、正本・台帳・実装・直接oracleを同じmaster IDで揃え、最後に旧仕様、重複owner/test、未変更領域checkを除去します。

## 定義・検証状態

- owner / master ID: owner registryの`PRODUCT`、`WIRE`、`DATA`、`UX`、`I18N`、`SECURITY`と、このページから辿る各master ID。
- 実装入口: `src/usage_store.rs`、`src/server.rs`、`src/main.rs`、`ui/`、`windows-client/`、`.github/workflows/`。
- 直接oracle: 各層別ページが示す単一ownerの直接caseと、`scripts/requirements_authority.py`によるowner/master ID整合。
- 未確認の扱い: ownerと実装が一致しない、current revisionの直接証拠がない、公開Wikiとrepository mirrorの同期を未確認の状態は`INCONCLUSIVE`です。この索引は不一致を正常化せず、実装済み・PASSを決めません。
