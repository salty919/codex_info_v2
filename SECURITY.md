# Security threat model and acceptance gate

Contract identifier: `SECURITY_CONTRACT_V7_2026-10-15`.

This versioned document defines the finite attack surface and controls owned by SECURITY. Changes must map affected assets, inputs, boundaries and controls to their registered direct oracles before implementation. The PRODUCT owner registry, WIRE resource contract and DATA admission rules determine the corresponding runtime contracts; an old route list or transport count cannot redefine valid recorded facts. Validation covers the changed boundaries and their direct consumers. It does not claim that unknown vulnerabilities cannot exist.

## Assets and trust boundaries

- Assets: Codex/ChatGPT account metadata, session history, local usage database, authentication URL, UI integrity, loopback APIの公開スナップショット, Windows監視クライアントの表示整合性, Linux update candidate and persistent installer/unit state, and the user's process privileges.
- Untrusted inputs: Codex app-server JSON-RPC, `thread/list` paths, session JSONL, migration/history files, environment-provided paths, authentication URLs, CLI port values, loopback HTTP requests, Windowsクライアントが読むloopback HTTP応答, fixed-repository public Release metadata/assets consumed by the Linux updater, X11 properties/events, and all strings rendered in the UI.
- Local same-UID administration of this repository and Codex installation is trusted. World/group-writable executables, paths outside the configured roots, symlinks crossing a root, malformed/oversized data, and another X11 client are not trusted.
- X11 cannot isolate clients on the same display. The application must not treat X11 as a confidentiality boundary; this residual platform limitation must be reported.

## Required controls

1. Resolve both the Codex executable and browser opener executable to absolute regular files before spawning them. Explicit overrides must be absolute and may not be symlinks. A PATH launcher symlink is accepted only after canonicalizing it to its final regular target; the target and every canonical parent are then validated. Reject a relative PATH entry, non-regular/non-executable target, or file/parent writable by group or other. WSL DrvFS is the one explicit compatibility case because it reports synthetic `0777`: accept a component only when `/proc/self/mountinfo` identifies its containing mount as `9p` with `aname=drvfs` and the component owner equals the process UID. This does not make Windows ACLs an application security boundary; the installed Codex binary remains part of the stated same-UID local administration trust assumption. Never invoke a shell; pass each argument directly to `Command`.
2. Parse authentication URLs structurally. Allow only scheme `https`; empty username; no password; host exactly `openai.com`/`chatgpt.com` or a DNS-label-boundary subdomain ending in `.openai.com`/`.chatgpt.com`; and no explicit port or port 443. Path and query are allowed, fragment is rejected. The entire input must be at most 2,048 Unicode scalar values. Pass an allowed URL as one structured process argument; never use suffix substring matching or a shell.
3. Accept `thread/list` rollout files only when their canonical regular-file path remains under the canonical Codex sessions root. Reject symlinks and paths outside that root.
4. Traverse session data without following symlinks. Limit inventory to depth 8 and 4,096 regular JSONL files, each whole-file snapshot input to 256 MiB, and each complete JSONL line to 4 MiB. Depth is the number of path components relative to the sessions root, including the file name; a file directly under that root has depth 1. Count all regular `.jsonl` inventory entries before selecting the collection prefix. These bounds are product resource limits, not limits promised by the external producer. Sort the validated inventory by metadata modification nanoseconds descending and canonical absolute path descending, then collect the longest whole-file prefix not exceeding exactly 2 GiB; the first file that does not fit and every older file are overflow, with no smaller-file hole filling. Inventory may exceed 2 GiB without making the selected candidate fail. Depth, file-count, applicable per-file, line, metadata, containment, or arithmetic failure remains fail-closed. DATA owns the distinct local-usage and live-rollout admission rules. Resident continuous recording uses its existing cycle byte budget and verified complete-record checkpoints rather than rejecting a growing source by total file size. Live rollout uses bounded-memory streaming of the entire fixed original prefix under the existing shared 15-second cycle deadline, including parse and hash reads; it does not inherit the whole-file snapshot size cap. Deadline exhaustion retains the last complete snapshot and does not admit a partial prefix. In local usage, preserve a malformed or oversized complete record and its unresolved range, do not claim a complete recorded marker, and continue only independently qualified later records. An unterminated local tail holds the cursor before that line and permits committing the preceding verified LF prefix; it does not manufacture a partial record. I/O or a source/containment failure rolls back that source's uncommitted candidate without stopping independent valid sources or quota. Live rollout keeps DATA's separate snapshot rejection boundary. Commit exact root-relative source markers in the same SQLite transaction as usage, and remove an overflow file only after a fresh marker read-back, canonical regular-file containment, unchanged device/inode/size/mtime, and a bounded `/proc` check prove that Codex does not hold it open. Unknown, changed, active, unrecorded, or legacy files are retained. Cleanup failure is nonfatal and must not change usage history, durable state, backups, reset hints, recovery JSONL, selected files, or the last-good public snapshot.
5. Limit each JSON-RPC line to 4 MiB bytes, require valid UTF-8, cap JSON nesting depth at 128, reject duplicate keys in every object instead of applying first/last-wins semantics, limit ignored/mismatched messages to 1,024 per request, and limit response wait to 15 seconds. Malformed, oversized, over-depth, duplicated-key, mismatched, stalled, or terminated responses become a concise user-safe error.
6. Reap the app-server child on Stop, channel closure, initialization failure, and every early-return path. Do not leave an orphan process.
7. Normalize external display text to one line before storing/rendering its display value: replace C0/C1 controls, CR/LF/tab, U+2028/U+2029, and bidi formatting/isolate controls with an ASCII space, then collapse consecutive spaces. Bound display values by Unicode scalar count: email 254, plan 64, model 128, thread title 512, limit name 96, and status 160. Over-limit email/thread-title/limit-name/status display strings are shortened to the first `limit - 1` Unicode scalar values plus `…`; this is never applied byte-wise. Do not apply this display transformation to account/session/model identity or source payloads. Canonical model IDs follow DATA's exact normalization and rejection rules, and wire IDs follow WIRE; invalid identity is rejected rather than repaired into another ID. Plan is an exact schema enum and schema-external values reject the response. AccountActivity's display label keeps its separate 24-scalar rule. Authentication URLs are rejected rather than shortened when over 2,048 scalar values. Validate every numeric field against its single owner in `docs/PRODUCT_REQUIREMENTS.md`, `docs/REST_API_V1.md` and `docs/DATA_PROTECTION_POLICY.md`; presentation follows `docs/WINDOWS_UX_SPEC.md`. Reject negative, fractional where an integer is required, non-finite-equivalent, out-of-domain, and overflow values. Never display raw JSON-RPC error objects or secret-bearing payloads.
8. Use parameterized SQLite statements and `Cargo.lock`. Create the application data directory with mode 0700 and database with mode 0600 on Unix; reject configured DB/session/migration roots that are relative, symlinks, non-directories where a directory is required, or escape their canonical configured root. Rust build/test validation commands use `--locked`; runtime `run.sh` never invokes Cargo.
9. Keep product source free of explicit `unsafe` unless a separately reviewed exception is documented. The crate uses `deny(unsafe_code)` rather than `forbid(unsafe_code)` because generated Slint code contains its own reviewed lint allowance; a source scan separately rejects explicit `unsafe` in `src/`, `build.rs`, and `run.sh`. Do not persist or print credentials, tokens, private keys, or authentication cookies.
10. The REST API always binds the numeric loopback address `127.0.0.1`; public CLI input can change only the port with `--port PORT`. Reject zero, overflow, negative, non-numeric, missing, duplicate, or malformed port values without falling back to a broader address. Permit only GET routes and exact query/header forms registered by WIRE, including stable health/runtime/accounts, v1/v2 compatibility details, v3/v4 current/history/threads and v5 directories. WIRE alone owns the exact route list, errors, cache headers and finite resource limits. Unknown routes return JSON 404, known routes with a different method return 405, and no CORS policy is emitted. HTTP parsing and connection lifecycle use Axum/Hyper. Handlers read immutable publication, not Slint, Codex RPC, authentication flows or SQLite. Persistent effects are restricted to DATA's existing fixed-field failure logger; payloads, credentials and raw errors are never logged. DATA admission, surface-level atomicity and WIRE schema/domain checks remain mandatory. A confirmed partial model set is valid data with explicit quality, not an invalid whole snapshot. Genuine history failure is isolated according to PRODUCT/WIRE and cannot erase independently accepted quota/model/thread facts. Loopback is a same-host boundary; documented Windows forwarding relies on SSH for peer authentication and encryption.
11. The Windows monitor uses the fixed numeric loopback service only. Health confirms readiness, not data collection success. Current, directory, history pages, threads, runtime/accounts and legacy exact-404 fallback follow WIRE; data from different versions, accounts or published pairs is never merged into one surface. No editable HTTP/LAN/Internet endpoint, authentication header, token, cookie, password or private key is accepted. Setup may accept an SSH user/host or SSH config Host alias only in transient memory and launch Windows ssh.exe directly with an argument list; input, commands, credentials, keys and resolved config fields are not persisted. HttpClient permits GET only to WIRE's fixed route/query allowlist and disables proxy use, redirects, cookies and automatic decompression. Enforce WIRE's header/body/per-page/schema limits before admission. There is no period-total limit of 128 and no aggregate calendar-month or multi-page limit borrowed from the legacy 31-day adapter. Model/thread limits are route/version-specific. Require application/json, exact required keys, no unknown/case-altered/duplicate keys, numeric/source-state domains and bounded text without control/bidi characters. Transport/validation failure retains the affected surface's independently accepted last-good state, shows a bounded localized error and does not clear unrelated surfaces. Per-request timeout is 1 second, with one in-flight cycle per surface owner; polling, positive Main bundle suppression, page collection and cancellation follow WIRE. Closing a surface cancels its work. Response bodies and exception text never reach UI or logs.
12. The Windows update client is a separate trust boundary and has no editable endpoint. It may GET only the public releases for exact repository `salty919/codex_info_v2`, the exact release manifest/installer asset for a validated `windows-vX.Y.Z` tag, and at most three HTTPS redirects restricted to `api.github.com`, that repository's `github.com/.../releases/...` paths, and `release-assets.githubusercontent.com`. Proxy, cookies, automatic decompression, automatic redirects, credentials, and request bodies are disabled. Release-list bytes are limited to 1 MiB, manifest bytes to 16 KiB, and Setup bytes to 256 MiB. Draft/prerelease releases, nonstable versions, unknown/duplicate/missing manifest fields, tag/version/name/URL/size/SHA mismatch, truncated/oversize content, and hash failure are rejected with no installer launch. Startup performs check-and-notify only. Network download and the ordinary interactive Setup launch occur only after the user activates the conditional update action; silent install, unattended apply, and automatic restart are prohibited. Partial files are removed and updater failure never replaces the loopback client's last-good snapshot or backend status.
13. The Linux updater is a separate trust boundary with no editable endpoint or credentials. It may read only the fixed repository's public HTTPS Release metadata and validated Linux asset. PRODUCT section 5 owns the exact resolver, archive digest verification, manual-bundle verification, installation transaction, rollback, deadlines and managed-readiness decisions. Automatic stable selection uses its single `releases/latest` response and Linux archive; Windows assets, unrelated assets, Release history count and external sidecars are not automatic-update admission conditions. Manual `--bundle` retains its separate checksum and external-manifest contract. Do not copy the publisher's member validation into a different runtime acceptance policy. Untrusted URLs, malformed required metadata or archive digest mismatch fail closed. Downgrade never becomes an update; an equal version repairs only an incoherent local generation. Installation owns the atomic journal/current switch and must preserve the verified old generation on failure. Successful running state binds the same source generation before and after the probe across the Recorder PID/starttime/executable and profile lock, and the REST PID/starttime/executable, listener FD and health. Only the embedded configuration may use one PID for both roles. An unknown or foreign owner is never signalled and yields explicit `SAFE_BLOCKED`, not success. No path uses Cargo, a repository copy, `target/`, or an artifact fallback. Remove affects only the registered recorder/REST/update units and retains installed generations, launcher/installer/manifest, profile data, and control/recorder/gap state. Journals never contain raw responses or secrets.

## Repository dependency audit (`SEC-DEPENDENCY-AUDIT-01`)

This additional read-only CI gate is separate from the application runtime threat model and normal quality owner selection. Every pull request to `feat/next` or `main` triggers the Rust, dependency-review, and dependency-metadata workflows without GitHub path filters, whose finite diff window can omit a later dependency change. Rust full-graph advisories/licenses/sources remain owned by the unchanged Linux `deny.toml`. The existing Windows locked restore owns NuGet direct/transitive auditing at low severity and above, uses explicit nuget.org package/audit sources, treats NU1900–NU1905 as errors, and stops before format/test on a restore failure. The metadata helper inventories all NuGet lock targets, hash-pinned Python declarations and inline suppliers, the actual existing PyYAML runtime version, and structured Actions references; it queries official license metadata and OSV for Python and exact Actions release versions resolving to the scanned commit. Actions without an exact version, implicit/unhashed Python supply, upstream Python dependencies lacking a lock, and licenses without an approved non-Rust policy remain explicit review requirements. Collection success is not legal approval or complete Actions tool/transitive coverage. No Rust allowlist is generalized to another ecosystem. Known advisories, failed metadata acquisition, invalid identity/schema, and incomplete OSV results fail the job; missing license fields remain review-required. DependencyReview owns supported PR graph deltas, while CodeQL/Codacy continue to own code/workflow static analysis. CI has contents-read permission, immutable action pins in the new workflow, no privileged PR-source job, and no new paid service. The governance caller executes both dependency contract test modules once; direct offline fixtures, native PowerShell exit cases, one real locked SDK restore, and one live metadata collection are the acceptance evidence.

## Failure behavior

Malformed structured input, numeric domain/overflow violation, unsafe path/executable/URL, authentication URL length overflow, and invalid API listener configuration are rejected. Display text follows control 7; identity is not display-normalized. On a first failure no synthetic quota/thread value is shown. Later transport/validation failure preserves the affected surface's complete accepted state atomically and marks it stale; account/logout boundaries follow PRODUCT's strict-empty contract. Independently accepted lane values and explicit partial/error state follow DATA/WIRE, and a failure in one history response cannot clear current or Threads. An invalid listener prevents startup rather than broadening the bind. The Linux updater does not mutate installation state before complete Release/archive validation. Any later install, service, or source-bound health failure ends only after the exact verified old generation is again managed and healthy; if an unknown/foreign owner makes that unsafe, it makes no signal or replacement and returns bounded `SAFE_BLOCKED`. Missing remote candidate uses a fully coherent local generation only, otherwise it also blocks safely. Either outcome shows only a bounded generic status, avoids opening a rejected URL or file, terminates/reaps an unusable child, and keeps Main/Graph responsive. Security failure must not trigger window recreation, size repair, destructive DB recreation, or unchanged retry loops.
